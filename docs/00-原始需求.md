# 三、项目定位

项目名称：SmartTicket AI

中文名称：企业智能工单分流与 AI 辅助处理平台

业务场景：一家虚拟 3C 数码电商企业的售后客服部门。

系统主要解决：

1. 客户问题依赖人工分类。
2. 工单人工分配效率低。
3. 客服需要手动查找订单、退款及物流信息。
4. 售后政策分散，知识检索耗时。
5. AI 回复缺乏可信依据。
6. 客服处理结果缺乏反馈和分析。
7. 工单处理可能发生超时、重复及遗漏。

项目采用：

**NLP 分类 + 业务规则引擎 + 智能派单 + SLA 管理 + RAG + 人工审核反馈。**

不做真实退款支付，不接真实电商平台，不允许模型自行执行高风险操作。

# 六、核心业务模块

## 模块一：工单管理

支持：

- 创建工单。
- 查询工单。
- 分页与条件筛选。
- 修改工单。
- 添加工单消息。
- 上传受控类型的附件（非核心，可按风险延期）。
- 指派客服。
- 修改优先级。
- 查看操作日志。
- 关闭与重新打开工单。

工单状态：

- NEW：新建
- PENDING_ASSIGNMENT：待分配
- PROCESSING：处理中
- WAITING_CUSTOMER：等待客户补充
- WAITING_EXTERNAL：等待第三方
- RESOLVED：已解决
- CLOSED：已关闭

必须定义合法状态转换，不允许任意修改。

所有状态变化记录操作人、时间、旧状态、新状态、原因。

需要处理并发更新，避免状态覆盖。

## 模块二：BERT 工单分类

支持六个主要类别：

1. 订单问题
2. 支付问题
3. 物流问题
4. 售后退款
5. 商品质量问题
6. 账户问题

训练三个模型进行对照：

- TF-IDF + RandomForest
- fastText
- BERT 微调

要求：

- 统一标签映射。
- 统一独立测试集。
- 防止相似数据泄漏。
- 记录随机种子。
- 保存训练配置。
- 保存模型与 Tokenizer。
- 输出混淆矩阵。
- 输出 Precision、Recall、Macro-F1。
- 记录推理延迟和资源占用。
- 分析误分类案例。
- 使用验证集进行置信度阈值选择。
- 低置信度进入人工待分类队列。

不能把 Softmax 结果直接视为真实正确概率。

## 模块三：诉求与实体提取

从客户文本提取：

- 订单编号
- 商品名称
- 时间信息
- 主要诉求
- 是否存在多个诉求
- 缺失的必要业务信息

实现策略：

- 明确格式字段优先使用规则和校验。
- 复杂自然语言使用 LLM 结构化提取。
- 使用 Pydantic 验证返回结果。
- 无法确认的信息返回 null。
- 禁止模型编造订单编号、交易状态等业务事实。

## 模块四：智能派单

根据：

- 工单类别
- 客服技能组
- 在线状态
- 当前负载
- 工单优先级
- 业务处理权限

完成分配。

实现规则：

1. 确定有资格处理的业务组。
2. 过滤无权限或不可用人员。
3. 按明确策略选择客服。
4. 无可用客服时进入等待队列。
5. 记录每次派单及重新分配原因。
6. 防止并发派单产生重复或异常负载。

初始阶段采用确定性的规则派单，不需要训练强化学习模型。

## 模块五：业务数据查询

建立模拟业务数据：

- 客户信息
- 商品信息
- 订单信息
- 支付记录
- 物流记录
- 退款记录

提供受控查询接口。

必须遵守：

- 客户只能查询自己的业务数据。
- 客服只能查询其权限范围内的数据。
- 不允许通过 Prompt 直接构造任意 SQL。
- 不允许模型自动修改退款或支付状态。
- 查询失败时明确返回异常。
- 不允许编造不存在的订单状态。

## 模块六：RAG 知识库

知识内容：

- 退款政策
- 退换货规则
- 保修政策
- 物流异常处理规范
- 支付异常处理说明
- 账户安全操作规范
- 客服处理流程

处理流程：

文档上传 → 文档解析 → 清洗 → 切块 → 元数据保存 → Embedding → 索引构建 → 检索。

检索采用：

BM25 + BGE Embedding + RRF 融合 + Reranker。

必须实现：

- 文档版本控制。
- 审核与发布。
- 文档生效及失效时间。
- 知识切块来源追踪。
- 索引一致性维护。
- 失效文档过滤。
- 检索结果引用。
- 没有足够依据时拒答。

必须对比：

- BM25
- 纯向量检索
- 混合检索
- 混合检索 + Reranker

评价 Recall@5、MRR@5、检索延迟。

## 模块七：RAG 辅助回复

输入：

- 当前工单。
- 工单历史消息。
- NLP 分析结果。
- 受控业务数据查询结果。
- 检索得到的有效知识证据。

输出：

- 建议回复内容。
- 引用的知识文档。
- 相关业务事实。
- 风险提示。
- 是否需要人工确认。

要求：

- 不允许编造订单、物流和退款状态。
- 不允许编造未检索到的政策。
- 不允许自动承诺赔偿。
- 不允许直接操作数据库。
- 不允许越权访问数据。
- 缺少信息时主动提示补充。
- 高风险业务需要人工确认。
- 对检索文档中的提示词注入进行防护。
- 所有 AI 回复默认是待审核草稿。

## 模块八：SLA 管理

工单分为 P0、P1、P2、P3 四个优先级。

实现：

- 首次响应截止时间。
- 解决截止时间。
- 临近超时提醒。
- 超时标记。
- 管理员升级。
- SLA 达标率统计。

第一阶段采用自然小时计时。

时限由数据库配置，不允许写死在多个代码文件中。

计时任务必须考虑重复执行、服务重启和幂等性。

## 模块九：人工反馈

客服可以：

- 采纳 AI 回复。
- 修改 AI 回复。
- 拒绝 AI 回复。
- 修改分类。
- 标记知识错误。
- 提交拒绝原因。

保存：

- AI 原始结果。
- 人工最终结果。
- 修正原因。
- 模型版本。
- Prompt 版本。
- 检索来源。
- 处理时间。

反馈数据经过审核后，才能进入新的模型训练集。

不允许自动把所有客服反馈直接作为正确标签。

## 模块十：数据分析

模型指标：

- Accuracy
- Precision
- Recall
- Macro-F1
- 混淆矩阵
- Recall@5
- MRR@5
- P50 / P95 延迟

业务指标：

- 派单正确率
- AI 回复采纳率
- 平均处理时长
- 首次响应时长
- SLA 达标率
- 工单重新打开率
- 单工单 AI 调用成本

所有指标必须使用真实的测试运行结果计算。

模拟业务测试与真实生产效果必须明确区分。
