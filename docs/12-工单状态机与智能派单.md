# 工单、派单和 SLA 基础事务

## 状态与权限

纯状态规则：`domain/tickets.py`；数据库事务：`services/tickets.py`。NEW 为创建事务内事件，提交后进入 PENDING_ASSIGNMENT。业务状态和 analysis_status 分开，未分类不代表工单丢失。

PROCESSING → 等客户/等外部/解决；等待状态先回 PROCESSING；已解决由客户/管理员关闭；七日内客户/管理员重开到等待分配。管理员可把活跃工单退回队列。禁止直接 PATCH 任意状态。

解决必须先有人工公开回复；内部备注和客户补充不算首次客服响应。客户补充 WAITING_CUSTOMER 自动回处理中，不暂停时钟。重开清除当前指派与类别、重新待复核、建立新 SLA 周期，旧解决/超时证据不清除。

所有实际状态变化记录操作者（系统为NULL）、UTC时间、old/new、reason、request_id。客户看进度时原因/内部字段脱敏。工单原始消息保留，通过补充消息修正，不覆写历史。

## 确定性派单

1. 类别为空返回 NEEDS_MANUAL_CLASSIFICATION 并记录尝试。
2. 根据启用规则和启用业务组找有技能、启用且角色为AGENT的成员。
3. 过滤不在线与容量已满成员，指定客服还需满足同样资格。
4. 按规则rank、负载/容量、最久未分配时间、客服ID、组ID选择。
5. 更新工单、指派历史、负载、事件同一事务提交；不成功进入明确等待原因。

等待原因区分NO_ROUTING_RULE、NO_QUALIFIED_AGENT、NO_ONLINE_AGENT、CAPACITY_FULL。管理员调用POST /admin/dispatch-next，从已分类队列按优先级、最早创建时间、ID取下一单，也可限定类别。队首无客服时不自动跳过。后台worker已处理分类/索引与SLA；批准的正式分类结果可触发一次规则派单，未配置或影子模型人工兜底。没有持续自动重派所有等待队列的承诺。

## 并发取舍

本期新增 dispatch_mutex(id=1) 单行锁，凡涉及容量、指派释放、优先级、客服可用性等变更先获取它，再锁工单/更新客服。MySQL 使用 SELECT FOR UPDATE 和 READ COMMITTED；同一时间串行处理派单相关短事务，以清晰换取吞吐上限。初始小规模场景可接受，后续高并发再考虑分组/客服锁，不能不经实测声称高吞吐。

创建和消息另外按操作者行锁串行化幂等键。消息不修改负载，不在持有工单锁后再申请派单互斥锁。外部模型或网络调用不能进入这些数据库锁事务。

ticket_assignments 的生成列：未结束时为 ticket_id，结束后NULL，唯一约束保证每工单一个有效指派。关闭/解决释放容量，等待客户/第三方仍占用；客服离线不丢弃已有工单。旧指派结束后保留历史；重新分配立即撤销旧客服的后续资源访问。

本轮只证明 SQLite 上的顺序容量约束、唯一约束和 ORM 版本防覆盖；**没有证明 MySQL 行锁并发行为**。`tests_mysql/test_concurrency.py` 已准备最后一个容量、双状态写和重复创建三种并发场景，需专门隔离库和授权后执行，不计入当前通过数。

## SLA 基础

自然小时策略只从 sla_policies 取，初始值集中在 db/bootstrap.py；周期保存快照。首次响应、解决截止时间从提交或重开开始；等待不暂停；升级仅收紧截止时间、降级不延长，记录所用政策。

SLA提醒、幂等扫描、人工超时升级与业务统计已实现。周期保存政策快照，提醒键唯一；后台停止后恢复扫描，不依赖内存定时器保存业务期限。源码services/operations.py，真实停止/恢复证据operational-recovery.json，统计分母与范围见13/14和21文档。

## 独立验收与追问

`tests/backend/test_ticket_flow.py` 跑完整闭环、幂等、版本、容量和重启；test_security_and_business.py 跑资源隔离/授权事实；test_constraints.py 验证生成列和陈旧Session；test_admin_and_sla.py 跑配置、优先级与SLA；队列原因有单独测试。
