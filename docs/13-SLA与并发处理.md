# SLA、并发与可恢复任务

现行入口：`services/tickets.py`、`operations.py`、`jobs.py`、`index_jobs.py`，以及 `scripts/run_worker.py`。自然小时计时，不暂停等待客户/第三方的周期；统一存UTC，界面按浏览器时区显示。

初始P0–P3政策只有 `db/bootstrap.py` 一处定义，显式初始化后业务始终读库。创建/重开保存政策版本快照及首次响应、解决截止时间。新政策只影响新周期；提高优先级收紧截止，降低不延长。内部备注和客户发言不计首次客服响应；公开人工回复或发送已审草稿才计。解决需要有公开客服回复。

后台每30秒扫描未解决周期，按快照warning_seconds生成临期/超时提醒。`sla_alerts(cycle_id,kind)`唯一，扫描由持久化互斥行串行化，重复执行不重复提醒。重启不依赖内存计时器，重新比较数据库截止时间即可补出逾期提醒。提醒是系统内记录，不是邮件/短信送达证明；管理员确认接手或人工提高优先级都有审计。

没有引入APScheduler：单实例轮询+数据库时限/任务已经覆盖当前可靠性需求，不重复维护另一套调度状态。分类任务租约2分钟、知识索引5分钟，领取时 `FOR UPDATE SKIP LOCKED`，持久化token和尝试次数；完成时检查token，过期工作者不能覆盖新领取者任务结果。分类器不可用直接保存人工兜底，不造预测；索引失败退避30秒×次数，最多3次后FAILED，可手动构建恢复。

派单采用全局dispatch_mutex行，再锁工单/相关负载，READ COMMITTED下重查规则、在线、角色、业务组和容量。策略为规则rank、负载比例、上次分配时间、客服/业务组ID稳定排序。结束旧指派、释放负载、创建新指派和工单变更同事务；条件生成列UNIQUE保证一个工单只有一个有效指派。全局锁简单、可解释，但限制吞吐，规模扩大再按组拆锁并固定顺序防死锁。

工单等版本实体要求expected_version，ORM更新带version条件，冲突返回409。消息/创建使用按用户串行化的幂等键，重放仍重查资源权限；草稿发送也重新校验输入版本、知识时效和业务上下文，消息与SENT状态同事务。审计表账号只有SELECT/INSERT权限。

统计口径：首次响应SLA分母是已响应或已到期周期，分子是截止前响应；解决SLA同理。未到期未完成周期不进入分母。响应/处理时长只对有完成时间的周期平均；重开率为cycle_no>1的不同工单数/所有有周期的工单数；采纳率为采纳或修改采纳/已审核草稿数。零分母返回null。派单正确率缺少独立人工真值，成本未配置核验价格，均不伪造数值。

验证：默认单元/集成测试覆盖时区、周期、状态、幂等、草稿失效与重复扫描；`tests_mysql`另用真实专用MySQL验证最后一个容量竞争、同版本状态竞争和同幂等键创建。SQLite不能证明InnoDB锁行为。备份脚本将全库一致性快照恢复到新建项目库，比较每表主键排序后的行数/SHA-256，不覆盖已有库。

追问：为什么自然时间等待仍计时？唯一约束和应用锁各解决什么？租约过期后旧结果怎么办？为什么SLA分母不能包含全部未到期单？为什么用全局锁而非一开始分布式锁？
