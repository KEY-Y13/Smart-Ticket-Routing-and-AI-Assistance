# 数据扩充与AI业务评审方案

2026-11-10用户已选择：虚构业务标准＋AI复核，适用于当前学习项目。执行结果见[本轮交付](23-本轮数据与业务评审交付.md)：最终1,238条中文分类数据，原282项完成AI评审。以下保留开始时方案；初译/大批次远程方案未通过门槛并已退役，未计入合格集，不应重试失败付费批次。最后采用7B本地翻译/改编、独立中文盲审和Codex抽检，验收对象是中文主诉标签与可用性，未宣称逐句双语忠实度全部通过。生产环境不纳入本轮。

## 数据目标与来源选择

目标先取得约2400–3000条候选，逐项检查后争取保留至少1800条六类中文样本。数量以真实去重、归组与审核后的清单为准，不通过替换商品名、编号或复制模板凑数。训练/验证/测试计划约1200/300/300，同源翻译、改写及模板必须同组；另设歧义、多诉求及超出业务范围的拒绝分类挑战集。

来源先核对发布者许可、固定版本和内容分布，再决定下载和使用。已发现Bitext零售电商语料：发布者数据卡说明为英语混合合成数据、46意图、44884条问答、CDLA-Sharing-1.0。它不是中文真实客户数据，原标签也不是本项目六类，不能直接算作已完成。若采用翻译或改编，保留原文ID、原意图、原文哈希、版本、数据许可和转换记录，排除客服回复中的政策承诺，不将其当成本项目知识依据。

来源：https://huggingface.co/datasets/bitext/Bitext-retail-ecommerce-llm-chatbot-training-dataset/blob/main/README.md

翻译工具候选为Helsinki-NLP/opus-mt-en-zh，其模型卡标注Apache-2.0；仍需核查实际可用权重格式、运行环境及翻译质量，不能因模型卡存在便记为已经执行。

来源：https://huggingface.co/Helsinki-NLP/opus-mt-en-zh/raw/main/README.md

## 项目业务基准

沿用six-primary-v1：订单、支付、物流、售后退款、商品质量、账户。以主要处理诉求决定标签，而不是看到关键词就分类。

- “耳机坏了，帮我排查”属于商品质量；“耳机坏了，我要办理退货”属于售后退款。
- 支付失败/异常扣款属于支付；已申请退款后的到账进度属于售后退款。
- 下单/修改收货信息属于订单；已发货运输轨迹属于物流。
- 无法确定、多诉求冲突或不在六类范围的内容，不强塞入账户类，进入待确认池。

知识基准使用本项目50篇虚构政策及其版本/有效期。复核只判断回复是否符合本项目给定政策，不宣称已经经过真实企业法务、客服主管或业务人员认证。

## AI评审的证据要求

1. 来源/生成、语义转换、复核、训练、盲测分开保存，保留真实方法和工具版本。
2. 全量检查重复、近重复、敏感信息、标签冲突、许可、语言和缺失字段；单纯程序通过不叫语义审核通过。
3. AI语义复核时尽可能先不展示原标签；记录判断、理由和分歧，争议内容不自动进入训练集。
4. 冻结测试集后再训练，不因模型分数不好改答案、删除难例或反复调测试集。
5. 分类看逐类Precision/Recall/F1、混淆矩阵、错误案例和人工兜底覆盖率；检索看相关性与拒答；回复看事实、政策、引用、越权承诺及是否该拒答。
6. 明确区分“AI复核的项目训练数据”和“人工金标准/企业认证”。既有人工复核记录不伪造，不把当前282条候选批量冒充已由用户亲自审核。

付费调用仍受原总预算60次约束，当前交付基线已用54次。不得通过新脚本、新数据库或直连供应商绕开账本/扩大上限。先采用公开来源与本地处理；若需要额外付费评审，再提出明确次数与费用预算。

## 第4点自动化边界的含义

目前分类后可以按规则派一次单；客服全忙时留下等待原因，后续不会持续循环自动重派，管理员需按需派下一单。真实退款执行指真的操作支付渠道打款，当前只查询状态。多租户指多家公司之间的数据隔离，区别于客户/客服/管理员三种角色。OCR是图片识字，语音是录音识别，多平台接入是接微信等外部渠道。它们不妨碍现有网页工单闭环，本轮不把这些原P2能力自动加入范围。
